# 03-Architecture Analysis — 架构分析

> 目标：让读者建立"系统由什么组成、怎么协作"的立体地图。

## 执行流程

### Step 0：模块优先级分级

在分析前，按依赖方数量、是否核心链路必经对模块分档，产出分级表写入章节开头：

| 优先级 | 判定标准 | 分析深度 |
| --- | --- | --- |
| 高 | ≥3 个依赖方，或核心链路必经 | 深度：契约 + 依赖 + 运行时 |
| 中 | 被 1-2 个模块依赖 | 标准：职责 + 关键接口 |
| 低 | 工具/辅助模块 | 简略：一句话职责 + 入口文件 |

分级依据写入章节，避免读者误解"遗漏"。被降级不意味不重要，而是分析资源有限聚焦。

### Step 1：确定模块边界

以 01 的清单为起点，对每个核心目录读公开接口（`__init__.py`、`index.ts`、包导出），列出关键类型/函数。目录名只是线索，职责结论必须来自接口与实现代码。

### Step 2：分析依赖方向

用 import/require 语句构建模块间依赖，整理分层结论与循环依赖检查。优先使用 `rg -n "^import |^from " --type py`（依项目语言调整）。

### Step 3：识别运行时进程

寻找进程/并发证据：入口启动逻辑、Dockerfile CMD、worker/队列消费者注册、线程池/事件循环。区分"单进程多线程"与"多进程协作"。

### Step 4：部署拓扑

仅采信声明性来源（Dockerfile、compose、k8s、CI、IaC）。仓库无部署声明时写"仓库未声明部署方式"，不虚构。

### Step 5：跨切面能力

定位日志、认证、错误处理、配置加载、中间件/拦截器的实现位置与挂载方式。

### Step 6：架构决策与风险

从代码事实反推设计意图，每条标注「静态推断」。风险必须指向具体位置并给缓解建议。

## 输出物

- `project-book/03-architecture.md`
- `project-book/.pipeline/03-architecture.json`

## 质量检查

```
✓ 每个模块职责结论是否基于代码而非目录名猜测？
✓ 是否有模块优先级分级表，且依据写明了？
✓ 依赖方向是否有分层结论与循环依赖检查？
✓ 是否无虚构部署拓扑？
✓ 结论是否区分了"观察到的证据"与"设计判断"（后者标注「静态推断」）？
✓ 是否无占位符残留？
```
