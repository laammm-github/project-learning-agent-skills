# 09-Architecture Review — 架构改进候选

> 目标：基于 01-05 的已有分析成果，识别可操作的架构改进机会，按优先级排序。
> 本阶段为**可选**，不纳入标准 10 章产物计数，需用户显式触发。

---

## 职责

- 只读复用 01-05 的分析成果，不重新扫描源码
- 产出优先排序的架构改进候选清单
- 每个候选给出 7 维评估
- **不修改任何生产代码**

---

## 执行流程

### Step 1：读取已有分析成果

从 `project-book/` 只读以下文件：
- `03-architecture.md`（模块边界、依赖方向、循环依赖、架构决策）
- `04-core-flow.md`（核心链路、同步/异步边界、失败路径）
- `05-core-concepts.md`（抽象、契约、扩展点）

### Step 2：扫描改进机会

从以下维度扫描：

1. **循环依赖**：从 03 的依赖分析中提取，标记参与循环的模块
2. **职责过载**：模块承担了超过 3 个不相关的职责
3. **单向依赖违例**：低层模块反向依赖高层模块
4. **扩展点不足**：05 中标记的扩展点太少，或关键扩展点缺失
5. **测试边界模糊**：核心逻辑与 I/O 耦合，难以单元测试
6. **同步阻塞**：核心链路中同步调用外部服务且无超时/降级
7. **配置分散**：配置散落在多处且优先级链不清晰

### Step 3：生成候选条目

每个候选格式：

```markdown
### [候选编号]：[简短标题]

**痛点**：[具体问题描述，引用 03/04/05 的已有发现，附 `文件:行号` 证据]

**提议的职责边界**：[建议把什么移到哪里，新的边界什么样]

**受益方**：[哪些模块/团队/场景会改善]

**迁移/回归风险**：[迁移中可能引入的问题，需回归测试的范围]

**验证策略**：[如何验证改进有效，建议的测试/指标]

**7 维评分**（1-5 分，5 最高）：

| 维度 | 分数 | 说明 |
|------|------|------|
| 影响度 | X | [改进后改善多少] |
| 局部性 | X | [改动范围多集中] |
| 置信度 | X | [证据多充分，静态推断扣分] |
| 工作量 | X | [预估人天/复杂度] |
| 可逆性 | X | [改错了能回退吗] |
| 依赖方影响 | X | [对调用方 breaking change 程度] |
| 测试覆盖 | X | [现有测试能兜底多少] |

「静态推断」
```

### Step 4：排序输出

按综合得分（影响度 × 局部性 × 置信度 / 工作量）降序排列，前 3 个标记为"建议优先关注"。
